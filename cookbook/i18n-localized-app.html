Build a localised app that switches between English, Shona, and Ndebele

By the end of this recipe you'll have an I18nProvider at the root of your app, a useT() hook for every string, a locale picker in the header that persists across sessions, and an ICU-aware formatter that handles plurals, dates, and currencies correctly per locale — with English fallback when a translation is missing.

International 2 primitives · 1 block ~30 min React · @huchu/react

Overview

Three layers. A loader that fetches resource JSON, a provider that holds the active locale + the merged resource bag, and a useT() hook that components actually call.

The whole system rests on one rule: components never see strings, they see keys. t("auth.signin") renders "Sign in" in English, "Pinda" in Shona, "Ngena" in Ndebele — and the component doesn't know which. That separation is what lets a translator open a single JSON file, edit copy, and ship without ever touching JSX.

Missing keys fall back, never crash. When a Shona translation hasn't landed yet, the user sees the English source — not the raw t("foo.bar") identifier. Fallback is a UX guarantee, not a debugging aid.

Locale is sticky per device. The first visit detects from navigator.languages; every visit after reads the user's saved choice from localStorage. The picker writes, the loader reads, the provider re-renders. No server round-trip for a preference that's per-browser anyway.

Skip this recipe if your product is English-only and will stay English-only. The provider has a real cost — one render-time formatter per string — that you don't pay back unless you ship a second locale.

Step-by-step build

01

Model the loader and fallback chain as data, not branching code

The locale chain is a list of resource bags walked in order. resolve(key) returns the first hit — that's the whole algorithm. Per-locale fallbacks live in each pack's $meta.fallback field, so adding a regional dialect (e.g. sn-ZW falling back to sn falling back to en) is a JSON edit, not a code change.

02

Format every string through ICU — never string-concatenate

Plural rules differ per locale — English has one/other; some languages have more. Don't build a sentence with "You have " + n + " items"; pass n to an ICU template and let the formatter pick the branch. The browser ships the rules for free in Intl.PluralRules; the formatter wires them up.

Code-only step

Real apps use intl-messageformat. This is the floor that proves the contract.

Intl.PluralRules ships in every modern browser — no library needed for the rules themselves.

03

State-machine the provider so loading and locale switches are explicit

The provider has three states: idle (first mount), loading (fetching a new chain), ready (chain available, components render). Reducers make the transitions impossible to corrupt — a stale fetch can never overwrite a newer one because the reducer ignores results whose request id doesn't match the current one.

Code-only step

The reqId guard is the part that's easy to forget — without it a slow EN load can land after the user already picked SN.

First paint waits for the chain. That's the price of correctness — a blank 80ms is better than a Flash Of English Content.

Variations

Three common shapes the base recipe bends into.

Per-route lazy packs

If the app is large, ship only the keys a route uses. The loader becomes loadPack(locale, route) and the chain is route-scoped. Most apps don't need this until they cross 5 MB of resource JSON.

// per-route loader
loadPack('sn', 'pos')
  .then(p => mergeIntoChain(p));

Server-side default

If the app is SSR'd, set the initial locale on the server from the request's Accept-Language. Hydrate the provider with the resolved chain so the first render is already correct — no flash, no client refetch.

// pages/_app.tsx
<I18nProvider
  initialLocale={req.locale}
  initialChain={req.chain}
/>

Inline language toggle

For pages outside the app shell — sign-in, public docs — the picker doesn't live in the header. Drop a compact LocalePicker variant="inline" next to the title; same hook, different chrome.

<LocalePicker
  variant="inline"
  align="end"
/>

Accessibility

What the recipe takes care of so consumers don't have to.

  • The root <html lang> attribute is updated whenever the locale changes — screen readers switch voice automatically.
  • The locale picker is a SegmentedControl, which exposes role="radiogroup" with arrow-key navigation between options.
  • Date and number formatting goes through Intl.*, which respects the user's full locale tag including region (en-ZW uses Zimbabwean number separators, not American ones).
  • Missing keys render as ??key?? — visible to QA in screenshots and never block the user from completing a task.
  • The provider waits for the chain before first paint, so users never see a Flash Of English Content when they've selected another locale.
