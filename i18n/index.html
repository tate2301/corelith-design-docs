Internationalisation (i18n)

Every user-visible string lives in a JSON resource file keyed by ICU MessageFormat. The system ships English by default and resource packs for Shona and Ndebele — the languages an operator on a Zimbabwean shop floor is most likely to read fastest.

ICU MessageFormat Locale fallbacks Native Intl.* for dates & numbers

The model

Three rules. They are the whole contract.

  1. Every string is a key. Hard-coded copy never lands in components. Even a one-word button label is t("actions.save").
  2. Plurals and inserts go through ICU. Pluralisation rules differ per language. Don't string-concatenate — use {count, plural, one {# item} other {# items}} and let the formatter pick the right branch.
  3. Dates, numbers, currencies use Intl.*. The resource files carry copy, not formatting. Intl.DateTimeFormat(locale).format(d) is the one true date renderer.

Supported locales

English is the default and the source of truth. Any missing key in another locale falls back to English — never to the raw key.

English en

Default. Source of truth for every key. Every new key lands here first.

en.json

ChiShona sn

Primary operator language across most of Mashonaland. Falls back to en.

sn.json

IsiNdebele nd

Primary operator language in Matabeleland. Falls back to en.

nd.json

The resource files include a $meta block that names the locale, its writing direction, and its fallback. That metadata is what the loader reads to wire up the locale chain — never hard-code locale codes in your app.

Using t()

One function, one rule: pass a key and an optional values object. Never concatenate.

// In a React component (pre-alpha @corelithzw/react path)
import { useT } from '@corelithzw/react';

function Welcome({ user }) {
  const t = useT();
  return <h1>{t("auth.welcome", { name: user.name })}</h1>;
}

// Output (en): "Welcome back, Tendai"
// Output (sn): "Tigashire, Tendai"
// Output (nd): "Sikwamukela, Tendai"

For dates, numbers, and currencies, always go through Intl.* — never bake formatting into the key.

// Date
new Intl.DateTimeFormat(locale, { dateStyle: "medium" }).format(receipt.createdAt);

// Currency
new Intl.NumberFormat(locale, { style: "currency", currency: "USD" }).format(123.45);

// Relative time
new Intl.RelativeTimeFormat(locale, { numeric: "auto" }).format(-2, "day");
// en: "2 days ago"   sn: "mazuva 2 apfuura"   nd: "ezi-2 ezedlule"

Fallback chain

A missing key never shows the raw t("foo.bar") identifier. The loader walks the chain and stops at the first hit.

  1. Look up the key in the active locale's resource (e.g. sn.json).
  2. If absent, follow the $meta.fallback chain — for sn and nd that's en.
  3. If still absent, log a structured warning in development and return the English string.
  4. If the key isn't in any pack, return the key itself surrounded by question marks (e.g. ??auth.signin??) so QA spots it in screenshots.

Adding a string

The English pack is the source of truth. Every key starts there, then ships to other locales when translated.

  1. Add the key to i18n/en.json using scope.snake_name — e.g. approvals.escalate_to_owner.
  2. Use ICU placeholders for any insert — {name}, {count, plural, one {…} other {…}}.
  3. Open a PR. CI runs a check that every key in en.json exists in sn.json and nd.json (untranslated keys are flagged but not blocking — English fallback covers them).
  4. Translators ship the Shona / Ndebele strings in follow-up PRs.

RTL handling

Not in scope today — all three supported locales are LTR.

The $meta.direction field exists so an Arabic or Hebrew pack can declare itself "rtl" when we get there. tokens.css uses logical properties (margin-inline-start, padding-block) almost everywhere — see the RTL audit in the roadmap for the remaining sweep.
